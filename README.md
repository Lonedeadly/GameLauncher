# GameLauncher

Портативный лаунчер для моих игр. Читает публичные репозитории-витрины,
скачивает и обновляет игры, запускает их. Токенов и секретов не содержит —
всё, что он делает, доступно анонимно.

## Стек

.NET 10 (LTS) + WPF, публикуется как **один self-contained exe** под win-x64.
Сторонних зависимостей нет: HTTPS, JSON, распаковка zip, SHA-256 и оконный
интерфейс — всё из стандартной библиотеки.

Размер собранного файла ~59 МБ. Это цена того, что пользователю не нужно
ставить рантайм.

## Как определяется «есть обновление»

`build.json` лежит **внутри** zip, поэтому по нему нельзя сравнить версии,
не скачав архив. Вместо этого используется поле `digest` ассета, которое
GitHub отдаёт в JSON релиза:

    "digest": "sha256:97349d98...", "size": 1847390

Оно меняется ровно тогда, когда меняется сборка, и не зависит от того, что
тег `dev` никогда не двигается.

Роли разведены:

* `digest` — для **логики** сравнения (и для проверки целостности загрузки);
* `commit` из `build.json` — для **показа** пользователю.

Резерв, если у ассета нет `digest` (старые релизы): `size` + `updated_at`.

## Лимит GitHub API

Анонимно — 60 запросов в час на IP. Проверено, что **ETag его не экономит**:
условный запрос возвращает `304 Not Modified`, но `X-RateLimit-Used` всё
равно растёт. Поэтому защита — TTL-кэш на диске, а не условные запросы.

Бюджет невелик: `/releases` отдаёт все каналы сразу, так что одна витрина =
один запрос, и `/releases/tags/dev` отдельно дёргать не нужно.

Не тратят лимит API вообще:

* `raw.githubusercontent.com` — оттуда читается `catalog.json` (CDN-кэш ~5 мин);
* `objects.githubusercontent.com` — оттуда скачиваются сами zip.

## catalog.json

Список игр — данные, а не код. Добавить игру = правка этого файла, без
пересборки лаунчера и без новой сборки у друга.

Поля записи:

| поле | что это |
|---|---|
| `id` | идентификатор и имя папки на диске; латиница, без пробелов |
| `name` | название для показа |
| `repo` | витрина в виде `owner/repo` |
| `exe` | имя исполняемого файла в корне архива |
| `description` | описание для карточки |
| `defaultChannel` | `dev` или `stable`, канал по умолчанию |
| `image` | картинка; пока `null`, показывается заглушка |

`exe` — **отдельное поле, а не вычисление**. Оно не выводится ни из
названия игры, ни из имени репозитория: у VoxelEngine витрина называется
`VoxelEngine-Releases`, а исполняемый файл — `VoxelGame.exe`.

Имя архива тоже нигде не собирается по шаблону: в стабильном релизе оно
содержит тег (`Strelalka-v0.1.0-win64.zip`), в dev — слово `dev`. По
контракту в релизе ровно один asset, его и берём.

Поле `schema` нужно, чтобы старый лаунчер, увидев незнакомую версию
каталога, сказал «обнови лаунчер», а не упал.

## Что должно работать без GitHub

- **Витрина без релизов** — игра остаётся в списке с состоянием «сборок
  пока нет» и без кнопки «Установить». Это штатный случай, а не край:
  `VoxelEngine-Releases` пока пуст.
- **Каталог недоступен** — показывается последний известный список из
  сохранённой копии, а не пустое окно.
- **Сети нет вовсе** — установленные игры запускаются. Кнопка «Играть»
  не зависит от ответа GitHub ни в каком виде.

## Раскладка на диске

    <папка лаунчера>\
       GameLauncher.exe
       launcher.config.json      ← если папка записываемая, иначе %LOCALAPPDATA%

    <папка игр>\
       .gamelauncher             ← метка владения
       state.json                ← что установлено: канал, commit, digest
       cache\                    ← TTL-кэш релизов и последний удачный каталог
       .tmp\                     ← закачки и распаковка (тот же том!)
       Strelalka\
          Strelalka.exe  build.json  fonts\  sfx\

`.tmp` внутри папки игр не случайно: на том же томе `Directory.Move` —
атомарная операция. Через системный `%TEMP%` на другом диске она выродилась
бы в копирование, и смысл «поменять местами» пропал бы.

## Установка и обновление

1. скачать в `.tmp\dl-<guid>.zip`, попутно считая SHA-256;
2. сверить с `digest` из API — не совпало, выбросить;
3. распаковать в `.tmp\stage-<guid>\` (проверяя, что путь каждой записи
   после нормализации остаётся внутри stage);
4. убедиться, что в stage есть `<Игра>.exe` и `build.json`;
5. если игра установлена: `Move(игра → .tmp\old-<guid>)`;
6. `Move(stage → игра)`; если упало — вернуть `old` назад;
7. удалить `old`, записать `state.json`.

Подменяется папка целиком, поэтому файл, исчезнувший в новой версии,
исчезает и на диске — сравнивать деревья не нужно.

## Самообновление лаунчера

Лаунчер сам замечает свою новую версию и ставит её по кнопке. Зелёная
полоса появляется вверху окна, когда есть что ставить; когда нечего —
полосы нет, «у вас всё свежее» не новость.

Windows не даёт переписать работающий exe, поэтому обновление идёт в две
половины и в двух процессах:

1. текущий лаунчер качает файл, сверяет SHA-256 с `digest` релиза, кладёт
   рядом как `GameLauncher.new.exe`, запускает его с
   `--replace <старый путь> <pid>` и немедленно выходит;
2. новый процесс дожидается выхода старого, отодвигает старый файл в
   `GameLauncher.old.exe`, копирует себя на его место и запускает обратно.

Старый файл цел в любой момент времени: он либо на месте, либо переименован
и при неудаче возвращается. Остаться совсем без лаунчера нельзя. `.new` и
`.old` убираются при следующем старте — сразу после подмены нельзя, один из
двух ещё выполняется.

Ассет в релизе называется просто `GameLauncher.exe`, без версии в имени —
чтобы лаунчер искал его по постоянному адресу, как игры ищут свой zip.

### Версия

Версия берётся из тега при сборке (`v0.2.0` → `-p:Version=0.2.0`), в
репозитории не хранится: иначе номер в файле рано или поздно разошёлся бы с
номером на релизе. Локальная сборка остаётся `0.0.0`, пишет в заголовке
«сборка из исходников» и обновляться не предлагает — подменять собранное
руками релизным файлом не то, чего ждёт тот, кто его собрал.

Сравниваются номера версий (`System.Version`), а не отпечатки: у лаунчера
теги нормальные, в отличие от игрового канала `dev`, где тег не меняется.

### Чего это не умеет

Версия `v0.1.0` обновиться не может: она вышла до появления этого механизма
и флага `--replace` не знает. С `v0.1.0` на следующую версию придётся
перейти вручную, один раз. Дальше всё само.

Проверка своего репозитория стоит одного запроса к GitHub API на цикл
кэша — при двух играх это 12 запросов в час из 60.

## Самопроверка

Сервисы прогоняются без интерфейса — по живым витринам, с настоящей
установкой и настоящим запуском игры:

    GameLauncher.exe --selftest C:\путь\к\пустой\папке

Проверяются правила выбора пути, отказ писать в чужую папку, витрина без
релизов, каталог из сохранённой копии, чтение кэша релизов с диска,
запускаемость без сети и полный цикл установка → обновление → удаление.
Отчёт идёт в консоль и в `selftest.log`. Код возврата 0 — всё прошло.
Флаг `--keep` оставляет игру установленной.

## Проверка интерфейса

    GameLauncher.exe --uicheck C:\папка\с\играми

Поднимает окно, слушает диагностику привязок WPF, снимает окна в PNG и
выходит. Нужна потому, что ошибки привязок молчаливые: они не ломают
сборку и не роняют приложение, а просто оставляют поле пустым.

Так был найден неочевидный дефект: `ProgressBar.Value` связывается TwoWay
по умолчанию, и привязка к свойству только для чтения бросала исключение
при показе карточки — из-за чего правая панель оставалась пустой. Отсюда
`Mode=OneWay` в разметке. Проверено, что режим этот дефект ловит: с ним
код возврата 1.

## Сборка

    dotnet publish src/GameLauncher -c Release -o publish

Публикация релиза — пуш тега `v*`, дальше `.github/workflows/release.yml`.
Секретов не требуется: используется встроенный `GITHUB_TOKEN`.

## Известное неудобство

Файл не подписан, поэтому при первом запуске Windows SmartScreen покажет
«Неизвестный издатель» — «Подробнее» → «Выполнить в любом случае».
Это касается любого неподписанного exe, не только этого.
